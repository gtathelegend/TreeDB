# Unified Plan Lifecycle, Adaptive Selection & Runtime Replanning

## 1. Overview and Core Invariants

TreeDB Phase 63 establishes a unified, deterministic, and safe physical plan lifecycle. It coordinates the optimizer memo (Phase 60), physical plan validator (Phase 61), canonical physical plan fingerprinting (Phase 62), statement cache (Phase 44), and runtime cardinality/resource feedback (Phases 45–46).

The fundamental architectural invariants of this phase are:

> **Adaptive selection chooses among validated physical alternatives; it does not create or mutate physical plans.**

And:

> **Runtime feedback is advisory. Correctness must never depend on feedback being present or accurate.**

Under this architecture:
- Physical execution candidates are derived only from the optimizer memo exploration.
- Every candidate is assigned an immutable, structural `PhysicalPlanFingerprint`.
- Every candidate must be validated against relational schema, index, and operator contracts before it is eligible for execution.
- Runtime feedback may adjust cost and cardinality rankings among already-valid physical candidates, but it can never bypass validation or invent new execution strategies.
- Runtime replanning is deferred strictly to the **next execution (Execution N+1)**; running operator pipelines are **never** mutated mid-query.
- All adaptive feedback and cache states remain strictly **in-memory and transient**, ensuring restart persistence and recovery correctness.

## 2. Plan Lifecycle States

The physical query plan advances through discrete, explicitly modeled lifecycle states (`PlanLifecycleState`):

```text
                  Logical Plan
                       ↓
              Memo Representation
                       ↓
   [ Candidate ] ─── Exploration of physical alternatives
         │
         │  Physical Plan Validation (Phase 61)
         ▼
   [ Validated ] ─── Passed schema, index, operator, and resource contracts
         │
         ├─── Stored into Plan Cache ──► [ Cached ]
         │                                   │ (Cache Hit & Re-validation)
         ▼                                   ▼
   [ Selected ]  ─── Picked by AdaptivePlanSelector for execution
         │
         ▼
   [ Executing ] ─── Running through storage engine executor
         │
         ▼
   [ Completed ] ─── Runtime metrics observed & feedback recorded
         │
         ▼ (Schema/Index DDL, Stats Change, or Replan Decision)
  [ Invalidated ]
```

### Lifecycle States Definition
1. **Candidate**: Unvalidated physical plan alternative generated by the optimizer or memo group.
2. **Validated**: Physical plan proven to satisfy all schema, column demand, ordering, row goal, index, and operator invariants. Encapsulated in `ValidatedPhysicalPlan`.
3. **Cached**: Validated plan retained in the statement cache keyed by SQL, parameter planning signature, and catalog/index/statistics generations.
4. **Selected**: A validated candidate selected by `AdaptivePlanSelector` based on cost, properties, and runtime feedback.
5. **Executing**: Plan actively running inside a transaction's execution pipeline.
6. **Completed**: Execution finished, producing `QueryExecutionMetrics` that may be fed into `FeedbackRegistry`.
7. **Invalidated**: Stale plan marked due to DDL, statistics changes, or adaptive replanning trigger.

## 3. Candidate Sets and Canonical Identity

### `PlanCandidate` and `PlanCandidateSet`
Physical alternatives explored by the optimizer memo are organized into bounded sets (`PlanCandidateSet`, bounded by `DEFAULT_MAX_CANDIDATES = 16`).

Each `PlanCandidate` encapsulates:
- `plan`: The complete `PhysicalPlan`.
- `fingerprint`: A 128-bit SipHash-2-4 deterministic structural fingerprint (`PhysicalPlanFingerprint`).
- `properties`: Guaranteed output properties (ordering, row goals, required columns).
- `estimated_cost` / `estimated_cardinality`: Static optimizer estimates.
- `adjusted_cost` / `adjusted_cardinality`: Estimates adjusted by runtime observations and feedback EWMA.
- `resource_signature`: Resource bounds (memory budget, temp file limits).
- `validated`: Proof of validation (`Option<ValidatedPhysicalPlan>`).
- `state`: Current `PlanLifecycleState`.

### Separation of Structural Identity and Planning Context
Structural identity is strictly governed by `PhysicalPlanFingerprint`:
- Structural fingerprint hashes only operators, access paths, joins, filters, schemas, and resource signatures.
- Static statistics generation, runtime feedback observations, EWMA entries, and parameter bindings are excluded from the structural fingerprint.
- Runtime feedback is mapped via `FeedbackKey`, which combines table/operator context, parameter planning signatures, statistics generations, and optional physical plan fingerprints.

---

## 4. The Validation Safety Boundary

TreeDB maintains a strict validation boundary (`PhysicalPlanValidator`):
- Unvalidated candidates are not eligible for execution.
- If an unvalidated candidate is in a candidate set, `AdaptivePlanSelector` attempts validation using `PlanValidationContext`. If validation fails, the candidate is excluded.
- If all candidates fail validation, `AdaptivePlanSelector` returns an error, forcing replanning rather than executing invalid plans.
- Cached plans retrieved on cache hits are re-validated against active catalog and index state before reuse.

---

## 5. Adaptive Selection and Ranking Algorithm

Given a bounded set of validated candidates, `AdaptivePlanSelector` deterministically ranks them:

1. **Eligibility Filtering**: Exclude unvalidated candidates and candidates whose `ResourcePlanningSignature` exceeds active system resource limits.
2. **Feedback Adjustment**:
   - Locate matching feedback entries in `FeedbackRegistry` by fingerprint key or structural operator key.
   - Respect `min_observations` (default: 2) and `min_confidence` (default: 0.5).
   - Adjust cardinality and cost using EWMA error ratios, clamped by `max_cost_adjustment_ratio` (default: 20.0).
   - Apply disk spill penalties if spill events were observed.
3. **Deterministic Ranking Hierarchy**:
   If two or more candidates exist, they are ordered deterministically by:
   - **Primary**: Lowest adjusted cost (`adjusted_cost`).
   - **Secondary**: Lowest adjusted cardinality (`adjusted_cardinality`).
   - **Tertiary**: Guaranteed physical ordering preference (plans providing required sort order are preferred to avoid extra sort nodes).
   - **Quaternary**: Access path preference (Index-Only Scan > Primary Point Lookup > Secondary Range Scan > Full Table Scan).
   - **Quinary**: Deterministic hexadecimal fingerprint string (`fingerprint.to_hex()`).
4. **Hysteresis Evaluation**:
   Compare the ranked best candidate against `current_plan_fingerprint`.

---

## 6. Hysteresis and Anti-Flapping Rules

To prevent pathological plan flapping between near-equal plans (e.g. Plan A with cost 100 vs Plan B with cost 98), the selector enforces a hysteresis threshold (`switch_threshold`, default: 0.85):

$$\text{Switch only if: } \text{Cost}_{\text{alternative}} < \text{Cost}_{\text{current}} \times \text{switch\_threshold}$$

- Minor cost fluctuations below 15% improvement result in `ReplanDecision::KeepCurrentPlan`.
- Dominant signals exceeding 15% improvement trigger `ReplanDecision::SwitchToAlternative`.
- If the current plan is not in the candidate set or has become invalid, switching occurs immediately.

---

## 7. Resource and Row-Goal Awareness

### Resource Compatibility
Candidates requiring memory or temp space greater than current system allocations are disqualified during step 1 of selection:
- An in-memory hash join candidate is disqualified if system memory budget is lower than its required memory signature.
- An external merge join / disk spill candidate is chosen instead, preventing runtime OOM errors.

### Row-Goal Integration
For queries with `LIMIT` / `OFFSET`:
- Row-goal candidate requirements ($K = \text{OFFSET} + \text{LIMIT}$) are reflected in `estimated_rows_examined` and `estimated_qualifying_rows`.
- Bounded TopN sort plans are preferred over unbounded full-sort plans.
- Ordered index scans enabling early termination are recognized through `RowGoal` properties.

---

## 8. Parameter Planning Signature Isolation

Parameterized queries (`PREPARE ...`) isolate planning signatures (`ParamPlanningSignature`):
- Feedback collected for `id = 1` (selective point lookup) is isolated from feedback for wildcard scans or large ranges.
- The `FeedbackKey` incorporates `Option<ParamPlanningSignature>`.
- Runtime feedback from one parameter signature cannot pollute or alter plan selection for an incompatible parameter signature.

---

## 9. Plan Cache Lifecycle & Next-Execution Reoptimization

### Plan Cache Integration
1. On prepare or initial query execution, the optimizer memo generates candidates.
2. The best validated candidate is selected and cached alongside candidate fingerprints and planning validity (`PlanValidity`).
3. On cache hit:
   - Check catalog, index, and statistics generations.
   - Verify `needs_reoptimization` flag on `PlanCacheEntry`.
   - Re-validate cached plan against current schema.
   - If `needs_reoptimization` is set or feedback indicates a threshold violation, the entry is removed and replanned for execution N+1.
4. If feedback crosses the replan threshold during query execution, `mark_needs_reoptimization` is called on the cache key, safely deferring replanning to the subsequent execution.

---

## 10. No Mid-Query Plan Mutation

TreeDB strictly prohibits mid-query operator replacement:
```text
[Operator A Executing] ──X──► [Replace with Operator B Mid-Stream]
```
Replacing active operators mid-query introduces severe pipeline state corruption, iterator inconsistency, and transactional hazards.
Instead, adaptive decisions follow the **Execution N → N+1** model:
```text
Execution N ──► Record Feedback ──► Mark Replan ──► Execution N+1 Selects New Plan
```

---

## 11. Resilience and Adversarial Feedback Handling

Runtime feedback is advisory:
- Observations with `NaN`, `f64::INFINITY`, negative numbers, or corrupted metrics are rejected or clamped.
- If feedback entries are missing, corrupt, or invalid, the selector falls back gracefully to static cost-based estimates.
- Removing all feedback never alters query semantics, output row sets, sort order, or transaction behavior.

## 13. Concurrency and Persistence Limitations

- **Single-Threaded**: TreeDB remains single-threaded. No mutexes, concurrent worker threads, or background replanning threads are introduced.
- **In-Memory Only**: Feedback registries and plan cache entries are held in volatile memory. Restarting or crashing the database cleanly resets feedback without data corruption.
